数据核对里发现的事：

- **演示的动作对齐正确**：从记录的推杆位置执行 $a_t$，到达记录的下一个推杆位置，误差在 1e-5 像素量级；错开一步则误差约 12 像素。
- **演示里的奖励按「描述下一帧」处理**：用画面像素的重叠面积独立估计进度，与奖励还原值的相关系数为 0.996。
  对齐到第 $t+1$ 帧时平均绝对差最小（0.0175），但与对齐到第 $t$ 帧（0.0206）差得不多，这条证据不强；
  选 $t+1$ 还因为字段名是 `next.reward`。
- **整个数据集里没有成功的帧**。演示记录到的进度最大 0.90（没有一帧标为成功）；加噪重放最大 0.875，
  进度超过 0.8 的帧只占 0.01%；随机游走最大 0.64。演示为什么没有成功帧，原因没有查明（连每个回合最后一个动作之后的奖励也没到 1）；重放是从别的初始状态开环执行，块到不了目标。
- 加噪重放有 78% 的回合推动了块，随机游走有 96%。

验证：`uv run pytest` 93 项通过（其中 2 项依赖已缓存的演示，无缓存时跳过）；`ruff`、`pyright` 无报错；
演示的下载路径实际走过一遍，四个文件与缓存逐字节相同。

评测里看到的事：

- **成功率在底部并列**：7 个策略成功数为 0，只按成功率排不出先后；平均最大进度把它们分开了（0.110 到 0.646）。
  M4 算秩相关时要处理并列，并同时报告按最大进度排序的结果。
- **执行噪声主要破坏最后一段的精度**：`bc-noise0.02` 的平均最大进度（0.836）与 `bc`（0.833）相当，成功数却从 23 降到 12。
- `dp-step10000`（0/50）的成功数低于 `dp-step5000`（1/50），平均最大进度则更高（0.598 对 0.516）。50 个回合分不清这两者。
- 最早的探针（2000 步的行为克隆）是 1/50，已从注册表删除，运行记录还在。

留给 M3、M4 的三个数据问题：

- **块的朝向没有折回主值区间**：策略回合里 15% 的帧朝向超出 (−π, π]，范围 −11.9 到 7.4（物理引擎累计转角）。
  判定头的角度标签要先折回，或改为回归正弦与余弦。
- **成功常常只有一帧**：34 个成功回合里 14 个只有 1 帧被判为成功，进度在阈值 0.95 附近徘徊，成功回合的最大进度中位数只有 0.963。
  判定头在阈值附近的小误差就会翻转成功与否，M4 要报告「按最大进度」的一致性作为对照。
- **验证集里只有 1 个成功回合**：现在的切分不看回合是否成功。M3 之前改成按「是否出现过成功」分层，并重建数据集（指纹会变）。

### 这组数字要带着下面几条读

**1. 两个模型拿到的工具描述不是同一份，7B 拿到的是坏的。** 把服务端的日志开到 `OLLAMA_DEBUG=2`，能看到它实际送进模型的提示。
`qwen2.5:7b` 的那份里，工具描述是 Go 结构体的默认打印，不是 JSON：

```
{"type": "function", "function": {list_policies 列出当前任务已登记的全部策略（名称、算法、登记时间） {object <nil> <nil> [] {}}}}
```

`qwen3.5:0.8b` 拿到的是正常的 JSON（`{"name": "list_policies", "description": …, "parameters": {…}}`）。
这是推理服务与这个模型的模板之间的问题（模型是 12 个月前拉取的），不在本项目的代码里；换一个最普通的英文工具定义，结果一样。

**2. qwen7b 的 8 条「没有工具调用」是这样来的。** 把服务端渲染的提示原样交给不经解析的补全接口，8 条都输出了工具调用，工具名也对，
但 `arguments` 是一个裸数组（`["diffusion.steps=2000", "diffusion.lr=1e-4"]`），不是 `{"overrides": […]}`；
服务端的解析把这样的调用整个吞掉，回应里既没有文字也没有工具调用（输出的 token 数与原样输出一致）。
按 PLAN 的定义，这 8 条判「不合法」没有判错——模型的输出确实不是合法的参数对象；问题出在它拿到的提示上。

对照试验：同样的用例，把工具描述手工渲染成正常的 JSON（与服务端应有的渲染不保证逐字节相同），试了 6 条（其中 5 条在这 8 条里），
6 条都给出了形状正确的参数。其中 `handwritten/051`（`policy.stpes=1000 对吗`）把用户写错的键改成了 `steps`，按标准答案仍不算匹配。
8 条里另外 3 条、以及其余 16 条没通过的用例与渲染有没有关系，没有测。

**3. qwen08b 是带思考的模型，延迟的对比混进了这个因素。** 它的模板在助手开头加 `<think>`，平均输出 118 个 token（qwen7b 是 30），
所以参数量约为九分之一，延迟的中位数反而是 3.4 倍。它的 3 条「没有工具调用」：1 条（`handwritten/062`）在思考阶段用完了 512 个 token 的上限；
2 条（`get_run/seen1/0`、`get_run/seen1/1`）陷入重复同一个字符，被服务端中止（日志里是 `prediction aborted, token repeat limit reached`），
回应里的输入与输出 token 数都是 0，这 2 条在上面的平均 token 数里是按 0 算的（耗时照常计入延迟）。

**4. 种子不起作用。** temperature 0 下三个种子的回答逐字相同。「跑 3 个种子」在这套设置下量不到波动；要看波动得用别的办法（如关掉缓存重跑同一个请求，
或改 temperature），这一点还没有做。

**5. 工具描述在看过一次试跑结果之后改过一处。** 正式运行之前在 24 条用例上试跑过（两个模型，种子 0，结果在临时目录里，不在结果库里），
这 24 条是正式用例集的子集。看了失败的用例之后改了 `train_policy` 的 `overrides` 参数说明：原来没有写明扩散策略要用 `diffusion` 段的键，
而标准答案要求这样写；同时让工具拒绝写错段的覆盖项（原来会悄悄不生效）。这影响 `train_policy` 族的 26 条用例。
系统提示在试跑之前写定，之后没有改。PLAN 目前没有规定「改提示时用哪些用例」，见待决定第 3 条。

**6. 复核做到哪了。** qwen7b 没通过的 24 条逐条看过，没有发现检查器判错的；通过的用例没有抽查，qwen08b 的 119 条只看了分类统计。
PLAN 1.3 要求的「随机抽 20 条人工复核」还没有做。

实现过程中改正的一个错：报告最初按「用例数 × 种子数」算 Wilson 区间，三个种子相同时样本量虚增三倍
（全部用例上 qwen7b 的完全匹配率区间是 [0.896, 0.933]，改正后是 [0.879, 0.943]）。已改为按用例数算，并记入 PLAN 的修订记录。
比例与配对检验不受影响。
