## 1. 大模型应用层（RQ4、RQ5）

### 1.1 用例

两套用例，都在同一个固定工作区上运行（玩具任务，冒烟配置，建好数据集、评测集、策略库与评测结果）。

| 套件 | 内容 | 判定方式 |
| --- | --- | --- |
| `toolcall` | 单步：一句指令 → 一次工具调用 | 工具名与全部参数和标准答案逐字段比较 |
| `task` | 多步：要调用若干次工具才能回答或完成；含多轮指代、应当拒绝的请求 | 检查器核对最终回答里的事实、工作区的最终状态、有没有多余的改动、需确认的操作有没有被擅自执行 |

用例按「族」组织：一个族是一种意图（如「查某个策略的成功率」「比较两个策略」「把一句话变成训练参数」）。
每个族有若干条指令模板，模板里的槽位（策略名、数量、阈值）由种子确定的采样填入。标准答案由程序给出，不由模型给出。

三个桶，分开报告：

| 桶 | 含义 | 用途 |
| --- | --- | --- |
| `seen` | 模板出现在微调语料里，槽位取值是新的 | 看模型有没有学会这些说法 |
| `heldout` | 整族的一部分模板留出，不进语料；另有若干个族整族留出 | 看能不能推广到没见过的说法与意图 |
| `handwritten` | 人工编写的指令：Claude 起草、用户审改，微调开始之前冻结 | 不受模板的措辞限制；主结论看它与 `heldout` |

规模（目标值，建好之后把实际条数写进 PROGRESS）：`toolcall` 每个桶不少于 100 条；`task` 不少于 40 条；`handwritten` 不少于 60 条。

防泄漏的规则：

- 切分以组为单位：同一条种子指令的各种改写属于同一组，整组进同一边。
- 留出的模板与 `handwritten` 不进微调语料，有测试检查（按规范化后的文本比对）。
- 固定工作区里的名称（策略名、评测集名、数据集名）与微调语料里用的是两套，防止模型把名字背下来。
- 少样本提示里的示例只从语料的训练部分取。

### 1.2 指标

| 指标 | 定义 | 统计单位 |
| --- | --- | --- |
| 合法率 | 模型的输出能解析成工具调用，且工具存在、参数通过类型校验的比例 | 用例 |
| 完全匹配率 | 工具名与全部参数都和标准答案一致的比例。参数先规范化（数值按类型比较，字符串去首尾空白，可省略的参数按默认值补齐） | 用例 |
| 任务完成率 | `task` 用例里检查器全部通过的比例 | 用例 |
| 幻觉率（按回答） | 最终回答里至少有一个数字找不到出处的回答所占的比例 | 回答 |
| 幻觉率（按数字） | 最终回答里找不到出处的数字占全部数字的比例 | 数字 |
| 越权次数 | 未经确认就执行了需确认操作的次数（绝对数，目标是 0） | 次 |
| 延迟 | 单次模型调用耗时的中位数与 95 分位数；一个 `task` 用例从提问到回答的总耗时 | 调用、用例 |
| 用量与成本 | 每个用例的输入与输出 token 数；按配置里的单价估算的成本 | 用例 |

「出处」的定义：数字出现在本次会话的工具输出或用户输入里，允许百分比与小数互换、允许四舍五入到回答里写出的位数。
序号、列表编号这类不携带事实的数字不计（规则写在校验器的测试里）。幻觉率只衡量数字，不衡量文字性的错误。

比例一律配 95% Wilson 区间。两个模型配置之间的比较，用同一组用例上的配对检验（McNemar 精确检验），报告两边不一致的用例数与 p 值。
延迟不含命中缓存的调用，所有配置在同一台机器、同一个推理服务上测。

### 1.3 运行方式

- temperature 0；种子写进请求。每个配置在每套用例上跑 3 个种子，报告合并后的比例，以及种子之间最大与最小的差。
- 所有配置用同一份系统提示、同一套工具描述、同一套提示渲染与输出解析。
- 每个用例的完整对话留在运行目录里。结果出来后随机抽 20 条判定人工复核一次，复核发现的检查器错误记入 PROGRESS，修正后重新打分（不重新调用模型）。

### 1.4 比较与预期方向

选型（A1、A2，回答 RQ4）：本机的 7B 级通用模型、一个不到 1B 的小模型，可能再加微调前的约 1.5B 模型。

| 比较 | 预期 | 不符合预期时意味着什么 |
| --- | --- | --- |
| 7B 对不到 1B，`toolcall` 完全匹配率 | 7B 明显更高 | 这个任务比想的简单，或者用例太容易 |
| 结果校验开对关，幻觉率 | 开着更低 | 校验器没起作用，或模型本来就很少编数字（两种都要查原始对话） |
| 结果校验开对关，任务完成率 | 不下降 | 重答把原本对的回答改坏了 |
| `task` 完成率对 `toolcall` 完全匹配率 | `task` 更低 | — |

微调（A3，回答 RQ5），五种配置：

| 编号 | 配置 |
| --- | --- |
| C1 | 7B 通用模型，零样本 |
| C2 | 约 1.5B 的模型，零样本 |
| C3 | 约 1.5B 的模型，少样本提示（示例从语料的训练部分取，条数在看到评测结果之前定） |
| C4 | 约 1.5B 的模型 + LoRA，未量化 |
| C5 | 约 1.5B 的模型 + LoRA，量化后经本机推理服务 |

| 比较 | 预期 | 不符合预期时意味着什么 |
| --- | --- | --- |
| C4 对 C3，`heldout` 与 `handwritten` 的完全匹配率 | C4 更高 | 这个场景靠提示就够了，不值得微调。照实报告 |
| C4 对 C2，`seen` | C4 高得多 | 训练没生效，先查训练本身 |
| C4 在 `seen` 对 `heldout` | `seen` 更高，差距不大 | 差距很大说明只背了模板 |
| C5 对 C4 | 接近，略低 | 差得多说明量化或对话模板有问题 |
| C5 对 C1，延迟 | C5 明显更快 | — |
| C5 对 C1，`handwritten` 完全匹配率 | 不预设方向 | 两种结果都是结论 |
| C5 接回 Agent 对 C1，`task` 完成率 | C5 更低（只练了单步） | — |

### 1.5 止损条件

| 触发条件 | 应对 |
| --- | --- |
| A2：加了参数校验与一次重试之后，本机最强的模型在 `task` 上的完成率仍低于 50% | 如实报告为选型结果；由用户决定是否接一个云端模型做强基线 |
| A3：摸底发现本机微调单步过慢或数值不稳定 | 训练换到 4090，本机只做推理与评测 |
| A3：C4 在 `heldout` 上不优于 C3 | 先查语料（泄漏、标签错误）；最多再调两轮超参；仍不行则如实报告 |
| A3：微调后的权重进不了本机推理服务，或对话模板对不上 | 换另一种提供 OpenAI 兼容接口的推理服务；部署数字按实际走通的路径报告 |
| 任何一步耗时超出估计的两倍 | 砍 P1（先列计划再执行的对比、跨会话备忘、级联），不砍本节的评测方法 |

### 1.6 已知的局限（写报告时要写明）

- 固定工作区是玩具任务：评的是「会不会操作平台」，不是「懂不懂机器人」。
- 合成的指令与真实用户的说法有差距；`handwritten` 只能部分弥补，而且它由 Claude 起草。
- 幻觉率只管数字。
- 单人项目，没有独立的标注者；人工复核只有一个人。
- 本机模型的成本是 0 元，「成本」这一栏对它们只有 token 数与耗时有意义。

## 2. 神经仿真器（RQ1–RQ3）

M4 之前写定，届时补进这一节：可信视野的阈值取法；消融（仿真器训练预算、上下文帧数、成功判定方式）各自的预期方向；
秩相关在成功率并列时的处理；bootstrap 的重采样单位。

M2 的结果已经提出两点要在这里预先定下的事：17 个策略里有 7 个成功数为 0，按成功率排有大量并列；
34 个成功回合里 14 个只有一帧成功。所以除了按成功率，还要按回合内最大进度排序并报告一致性。
